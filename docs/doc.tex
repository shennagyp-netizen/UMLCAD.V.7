\chapter{Document Purpose and Reading Rules}

This handbook documents the architecture and engineering state of UMLCAD.V.7 as a whole. It is deliberately more precise than a marketing overview and more compact than a raw source dump. The document describes the repository as an engineering system: authority, ownership, contracts, state transitions, deterministic identity, mathematical guarantees, provider boundaries, testing, deployment shape, and known limits.

There are two separate truths that must never be confused:

\begin{tabularx}{\textwidth}{@{}p{0.23\textwidth}X@{}}
\toprule
Term & Meaning \\
\midrule
\current & Code and files verified to exist in the current \texttt{main} repository state. \\
\target & Architectural direction expressed by the current development law and the architecture implied by the requested System-CAD model. It may not yet have an implementation on \texttt{main}. \\
\bottomrule
\end{tabularx}

A class, interface, endpoint, test, or documentation statement is not by itself proof that a capability is complete. Completion requires the semantic path, authoritative behavior, failure semantics, determinism, required tests, and applicable end-to-end evidence.

The mathematical roadmap M0-M16 is closed for its declared certified domains. That closure means the mathematical authority is treated as the existing foundation for the next system-CAD layer; it does not mean every possible CAD mathematical operation is implemented.

\section{Repository fact at the audit point}
At the audit point, the repository contains the mature Rust mathematical/native foundation, the existing \texttt{UMLCAD.Framework} and \texttt{UMLCAD.Kernel.Client} .NET surface, the legacy TypeScript kernel API, the OCCT backend/contracts, the demo/E2E harness, and the CI workflows described later. Some newer System-CAD domain projects described in earlier handbook text are not present on the exact current \texttt{main} tree and are therefore documented here as target architecture rather than current implementation.

\section{Authority hierarchy}

\begin{enumerate}
\item \textbf{Rust mathematics}: normative numerical authority for the mathematical contracts it declares and certifies.
\item \textbf{System-CAD semantics}: authoritative owner of CAD meaning, product meaning, engineering intent, references, evaluation orchestration, lifecycle state, and downstream domain composition.
\item \textbf{Providers/adapters}: implementation mechanisms behind stable service contracts.
\item \textbf{Representation/viewer}: derived consumer assets only; never authority.
\end{enumerate}

The Rust kernel is intentionally thin. The complete CAD system must not be compared with it as though they were equivalent architectural layers.

\chapter{System-CAD Domain Architecture}

The long-lived System-CAD architecture is organized around meaning rather than a list of applications.

\section{Core semantic ownership}

CAD Core owns, where applicable:

\begin{itemize}
\item Product, Part, Body, Sketch, Feature, Assembly, Occurrence, and product-structure semantics.
\item Design intent, parameters, constraints, references, publications, and configuration/context.
\item Coordinate-frame semantics and transforms.
\item Evaluation planning and dependency closure.
\item Deterministic semantic/evaluation/result identity.
\item Cache and invalidation semantics.
\item Authoritative results, provenance, topology evolution, and diagnostics.
\item Drawing and PMI meaning.
\item Product Structure and BOM semantics.
\item Integration contracts consumed by Sheet Metal, CAM, Simulation, and PLM.
\end{itemize}

The mathematical kernel supplies computations, not these meanings.

\section{Science}
Science owns scientific facts and services that can be reused by multiple engineering domains. Material and physical properties belong here. The Phenomena Simulation Service is an abstract, provider-neutral service boundary.

\section{Phenomena Simulation Service}

The stable boundary is:

\begin{lstlisting}
Engineering Consumer
        -> IPhenomenaSimulationService
        -> IPhenomenaSimulationProvider
        -> Simulation Implementation
\end{lstlisting}

The service does not encode whether the provider is internal, external, CPU-based, GPU-based, specialized, or remote. Provider identity, execution detail, and transport belong behind the contract unless the service explicitly makes them semantic inputs.

A simulation result must carry enough identity, inputs, assumptions, and provenance for the consumer to decide whether the result is applicable. A visually plausible scalar without provenance is not an authoritative engineering result.

\section{Engineering Resources}

Engineering Resources own reusable manufacturing/engineering facts and capability declarations:

\begin{itemize}
\item Machine.
\item Tool.
\item Fixture.
\item Process.
\item Capabilities.
\end{itemize}

CAM and Sheet Metal consume these resources; the resource model must not become hidden CAM state.

\section{Sheet Metal}

Sheet Metal owns sheet-metal design semantics. It consumes engineering resources and applicable science/simulation contracts. Material/machine/process feasibility validation is a cross-domain responsibility implemented through explicit contracts, not by allowing Sheet Metal or CAM to become a second CAD kernel.

\section{CAM}

CAM consumes authoritative CAD semantics, product structure/BOM, engineering resources, material/process information, applicable Sheet Metal outputs, and the Phenomena Simulation Service where needed.

The manufacturing chain is:

\begin{lstlisting}
Manufacturing Definition
        -> Toolpath
        -> Postprocessor
        -> Deterministic G-code / NC
\end{lstlisting}

The postprocessor is a semantic boundary. Machine configuration, tool, fixture, process, coordinate system, operation order, postprocessor version/configuration, and other declared deterministic inputs must participate in the relevant identity. A renderable toolpath is not itself machine-ready NC.

\section{CAD Product Structure and BOM}

Product Structure owns product composition. BOM is a derived semantic view:

\begin{lstlisting}
CAD Product Structure
        -> BOM
        -> Drawing / CAM / PLM
\end{lstlisting}

BOM must not be a competing source of truth. Quantities, variants, configuration, occurrence identity, and product references remain traceable to the authoritative product state.

\section{Drawing and PMI}

Drawing consumes authoritative CAD and product semantics. It may derive geometry, sections, dimensions, annotations, and BOM views for documentation, but it must not reconstruct engineering truth from presentation meshes. Drawing details are mapped against the declared external capability set; the viewer remains downstream.

\section{PLM}
PLM consumes authoritative product, revision, lifecycle, configuration, and related engineering metadata. It may own lifecycle/workflow records but does not become geometric authority.

\chapter{Specification - Evaluation - Result - Representation}

A central invariant is:

\begin{center}

\section{Specification}
Specification stores intent: definitions, parameters, constraints, references, configuration, declared relationships, and source identity. It should not store hidden mutable evaluation state.

\section{Evaluation}
Evaluation resolves dependencies, constructs deterministic requests, calls the canonical evaluator/adapter, integrates authoritative results, and computes derived assets when required.

\section{Authoritative Result}
An authoritative result is trusted semantic evidence. It must identify what was evaluated, under which inputs and configuration, with which authority, status, and provenance. Topology and reference correspondence are evidence, not guesses.

\section{Representation}
Representation is disposable consumer data. It may be regenerated without changing semantic truth. Rendering may use approximations that are unacceptable as authoritative geometry.

\chapter{References, Topology, Frames, and Identity}

\section{Reference semantics}
A reference is semantic. It is not an accidental array index. The system must be able to state the producer, expected result identity, semantic target, frame requirements, and selector restrictions.

Required resolution states are:
\begin{lstlisting}
Resolved
Missing
Ambiguous
Indeterminate
Unsupported
\end{lstlisting}
Arbitrary fallback is forbidden.

\section{Topology provenance}
When topology changes, a downstream consumer must have explicit correspondence/evolution evidence. Topology array order is never semantic identity.

The mathematical layer contains explicit topology support for vertices, edges, coedges, wires, faces, shells, incidence, orientation, closure, shell connectivity, and certified planar/solid domains. Broader curved-face sewing and unrestricted topology construction remain separate contracts.

\section{Coordinate-frame semantics}
Where applicable, distinguish World, Document, Part, Body, Sketch, Face, Occurrence, Drawing View, and Simulation frames. Feature direction is an oriented semantic value, not an interpretation of viewer camera state.

\section{Deterministic identities}
The current .NET Framework canonicalization is explicit:
\begin{enumerate}
\item validate required IDs and definitions;
\item sort configuration and semantic collections by ordinal identity;
\item serialize canonical semantic content using camel-case JSON without indentation;
\item compute SHA-256 over canonical bytes;
\item attach the resulting lowercase hexadecimal value as \texttt{BuildIdentity}.
\end{enumerate}
The canonical semantic schema is \texttt{uml-cad-semantic/1.2.0}; the current bridge package is \texttt{uml-cad-build-package/1.0.0}; the compiled model schema is \texttt{uml-cad-compiled-model/1.1.0}.

\section{Builder validation}
The current builder rejects empty/whitespace required values, duplicate definition IDs across parts and assemblies, duplicate occurrence IDs within an assembly, references to unknown definitions, and circular assembly references.

\section{Part semantics}
A part contains sorted parameters, geometry descriptors, constraints, references, components, part type, name, and structured metadata. Metadata supports part number, description, material, manufacturer, vendor, revision, lifecycle state, author, document code, and custom properties.

The current Framework geometry/constraint descriptors are semantic descriptions. They are not the Rust mathematical geometry types. This is the intended separation between system meaning and mathematical execution.

\section{Assembly semantics}
Assemblies contain occurrences. Each occurrence has definition identity/type, stable name/ID, transform, metadata, optional configuration, quantity, BOM structure, visibility/suppression, grounded state, and flexibility state. Nested assemblies are recursively represented.

\section{Drawing semantics}
A drawing contains stable sheets, part references, and settings. Sheets contain IDs, names, drawing references, and settings.

\section{Build history}
\pathref{dotnet/src/UMLCAD.Framework/Semantics/BuildHistory.cs} stores build snapshots in a synchronized in-memory history. Sequence numbers identify history entries and are deliberately not used as semantic build identity.

\chapter{Compiled Model Contract}

\pathref{dotnet/src/UMLCAD.Framework/Semantics/CompiledModel.cs} defines the current compiled-result graph.

\section{Package}
\texttt{CompiledModelPackage} contains schema, application identity, build identity, manifest, optional render artifact, and diagnostics.

\section{Manifest}
\texttt{CompiledModelManifest} contains root node IDs, nodes, relationships, representations, topology bindings, source bindings, diagnostics, and repeated application/build identity.

\section{Nodes and relationships}
\texttt{CompiledNode} carries ID, name, kind, parent/children, metadata, relationship IDs, representation IDs, capabilities, optional source, and state. \texttt{CompiledRelationship} carries a stable relationship ID, source ID, target IDs, kind, and metadata.

\section{Representations and provenance}
\texttt{CompiledRepresentation} identifies a consumer artifact, render node, bounds, capabilities, and selectable sub-targets. \texttt{CompiledTopologyBinding} bridges a semantic node to a render primitive and includes topology kind, artifact identity, naming/nomenclature, optional number, bounds, and metadata. This bridge never becomes geometry authority.

\section{Graph construction}
The compiler:
\begin{enumerate}
\item emits parts and assemblies in stable ordinal ID order;
\item creates URI-encoded definition IDs;
\item creates deterministic occurrence IDs;
\item recursively emits nested assembly and part children;
\item emits explicit constraint-reference relationships;
\item identifies root definitions not referenced by another assembly;
\item validates parent/child consistency and relationship resolution;
\item rejects duplicate node IDs.
\end{enumerate}
URI encoding prevents colons/slashes in user identifiers from causing structural collisions.

\section{Failure mapping}

Caller cancellation is propagated. A response body is size-limited while streaming, not merely after deserialization.

\section{Result validation}
The client validates submitted build identity, manifest identity, application identity/version, unique node IDs, root resolution, relationship source/target resolution, and render-artifact build identity. Therefore valid JSON is not equivalent to a valid result.

\chapter{Rust Snapshot and Constraint Semantics}

\pathref{kernel/math/snapshot.rs} defines the data structure consumed by the native mathematical API.

\section{Geometry}
Current exact semantic geometry includes points/lines/circles/arcs represented in the Rust mathematical geometry module. Geometry items have stable semantic IDs and parameter dependencies.

\section{Constraints}
The current constraint families include horizontal, vertical, coincident, fixed, and distance constraints.

\section{Relations}
The relation system includes parallel, perpendicular, equal-length, angle, collinear, concentric, equal-radius, radius, diameter, tangent, midpoint, point-on-line, point-on-circle, distance-points, symmetry, and related declared families.

\section{Solver authority}
The production solver uses analytic Jacobian rows for the supported equation set. Finite differences remain an independent verification mechanism and are not the production Jacobian authority.

\section{Mathematical non-claims}
General concave/holed/freeform trimmed-surface filling, unrestricted curved-face sewing, universal B-Rep Boolean construction, arbitrary edge filleting/chamfering, universal closest-point/intersection engines, and broad accelerator equivalence outside declared contracts are not silently included.

\section{Numerical policy}
CPU \texttt{f64} is the normative reference. GPU implementations accelerate explicit workloads. Tolerances are explicit inputs. Unsupported, ambiguous, singular, degenerate, non-finite, or indeterminate states fail closed.

\section{Solver detail}
\texttt{SolveOptions} currently defaults to maximum 100 iterations, residual tolerance \texttt{1e-8}, step tolerance \texttt{1e-10}, and initial damping \texttt{1e-3}. The finite-difference step remains for API compatibility and independent verification; it is not used to generate production Jacobians.
