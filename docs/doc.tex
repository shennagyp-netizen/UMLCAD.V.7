\chapter{Document Purpose and Reading Rules}

This handbook documents the architecture and engineering state of UMLCAD.V.7 as a whole. It is deliberately more precise than a marketing overview and more compact than a raw source dump. The document describes the repository as an engineering system: authority, ownership, contracts, state transitions, deterministic identity, mathematical guarantees, provider boundaries, testing, deployment shape, and known limits.

There are two separate truths that must never be confused:

\begin{tabularx}{\textwidth}{@{}p{0.23\textwidth}X@{}}
\toprule
Term & Meaning \\
\midrule
\current & Code and files verified to exist in the current \texttt{main} repository state. \\
\target & Architectural direction expressed by the current development law and the architecture implied by the requested System-CAD model. It may not yet have an implementation on \texttt{main}. \\
\bottomrule
\end{tabularx}

A class, interface, endpoint, test, or documentation statement is not by itself proof that a capability is complete. Completion requires the semantic path, authoritative behavior, failure semantics, determinism, required tests, and applicable end-to-end evidence.

The mathematical roadmap M0-M16 is closed for its declared certified domains. That closure means the mathematical authority is treated as the existing foundation for the next system-CAD layer; it does not mean every possible CAD mathematical operation is implemented.

\section{Repository fact at the audit point}
At the audit point, the repository contains the mature Rust mathematical/native foundation, the existing \texttt{UMLCAD.Framework} and \texttt{UMLCAD.Kernel.Client} .NET surface, the legacy TypeScript kernel API, the OCCT backend/contracts, the demo/E2E harness, and the CI workflows described later. Some newer System-CAD domain projects described in earlier handbook text are not present on the exact current \texttt{main} tree and are therefore documented here as target architecture rather than current implementation.

The components have distinct responsibility:

\begin{itemize}
\item \textbf{Specification}: immutable engineering intent, parameters, constraints, references, configuration, templates, components, product structure, and domain definitions.
\item \textbf{Reference resolver}: resolves producer/result/topology/frame/publication semantics and returns explicit Resolved, Missing, Ambiguous, Indeterminate, or Unsupported states.
\item \textbf{Dependency graph}: records explicit semantic dependencies and deterministic evaluation order; cycles are invalid.
\item \textbf{Evaluation planner}: computes dependency closure, cache eligibility, required evaluator and required mathematical contract.
\item \textbf{Evaluation engine}: orchestrates the semantic computation and integrates authoritative results without owning mathematical algorithms.
\item \textbf{Kernel contract/client}: constructs and transports explicit backend-neutral mathematical requests and validates response schema, identity, status, completeness and cancellation semantics.
\item \textbf{Result integration}: maps mathematical evidence into an authoritative System-CAD result without losing identity, frame, provenance or status.
\item \textbf{Topology/provenance}: preserves semantic topology bindings and evolution evidence; topology array order is never identity.
\item \textbf{Representation}: creates viewer, SVG, drawing, manufacturing and simulation display artifacts downstream of authoritative results.
\end{itemize}

\chapter{C4 Level 4 - Critical Runtime Paths}

\section{Feature evaluation}

\begin{lstlisting}
Feature Specification
 -> resolve references
 -> resolve frames/configuration
 -> close dependency graph
 -> construct deterministic evaluation identity
 -> select evaluator
 -> create mathematical contract
 -> invoke kernel authority
 -> validate authoritative result
 -> integrate topology/provenance
 -> update cache/invalidation
 -> derive representation
\end{lstlisting}

\section{Sketch attached to a face}

\begin{lstlisting}
Authoritative Face Publication
 -> semantic FaceReference
 -> derive Sketch frame from face semantics
 -> create sketch geometry/constraints
 -> solve through explicit mathematical contract
 -> authoritative Sketch result
 -> validate profile
 -> consume result in feature evaluation
\end{lstlisting}

Viewer camera state never supplies feature orientation or sketch-frame truth.

\section{Product / Assembly / BOM}

\begin{lstlisting}
Part Definition
 -> Assembly Occurrence
 -> occurrence transform/context
 -> Product Structure
 -> derived BOM
 -> Drawing / CAM / PLM consumers
\end{lstlisting}

An occurrence transform places an instance; it does not mutate the source Part definition. BOM remains derived from Product Structure.

\section{Drawing / PMI}

\begin{lstlisting}
Authoritative CAD/Product state
 -> Drawing Definition
 -> Sheet
 -> View / Projection / Section / Detail
 -> Dimension / Tolerance / GD&T / PMI
 -> derived drawing graphics
\end{lstlisting}

Drawing objects remain semantically traceable to authoritative CAD/product state.

\section{CAM}

\begin{lstlisting}
Authoritative CAD/Product/BOM
 -> Manufacturing Definition
 -> Setup / Coordinate System
 -> Operation / Strategy
 -> Toolpath
 -> Postprocessor
 -> deterministic G-code / NC
\end{lstlisting}

A rendered toolpath is not machine-ready NC.

\section{Phenomena simulation}

\begin{lstlisting}
Engineering domain
 -> Phenomena Simulation Service
 -> provider / adaptor
 -> simulation implementation or application
 -> verified simulation result
 -> engineering consumer
\end{lstlisting}

The adaptor is a phenomena-service boundary, not an application-semantic boundary. It may use multiple interchangeable simulation implementations, including remote or external applications. CAM may consume this service for process/physical validation.

\chapter{Mandatory Early System-CAD Vertical Slice}

The first system-level CAD proof is intentionally narrow and architectural:

\begin{lstlisting}
Create Cube
 -> select Face semantically
 -> Sketch on Face
 -> Circle A + Circle B
 -> solve/validate supported constraints
 -> Feature A along +FaceNormal
 -> Feature B along -FaceNormal
 -> recompute
 -> authoritative B-Rep / result
 -> topology + reference provenance
 -> derived representation
 -> viewer semantic selection
\end{lstlisting}

The slice proves the semantic path rather than merely a visual result. It must establish semantic intent, reference resolution, frame correctness, dependency planning, explicit kernel contract use, authoritative result integration, topology provenance and representation derivation.

Exact circular geometry must not be replaced by a polygon solely to make the workflow executable. When a required exact circular-profile solid or Boolean topology operation is not certified by the mathematical authority, that boundary remains explicitly unsupported until a new mathematical contract is established.

\chapter{System-CAD Domain Architecture}

The long-lived System-CAD architecture is organized around meaning rather than a list of applications. The normative architecture, C4 Level 1--4 decomposition, canonical evaluation path, domain boundaries, template/component/sheet semantics, phenomena-simulation adapter boundary, and mandatory early vertical slice are maintained in \pathref{docs/SYSTEM_CAD_ARCHITECTURE.md}. The sections below summarize those rules for the handbook.

\section{Core semantic ownership}

CAD Core owns, where applicable:

\begin{itemize}
\item Product, Part, Body, Sketch, Feature, Assembly, Occurrence, and product-structure semantics.
\item Design intent, parameters, constraints, references, publications, and configuration/context.
\item Coordinate-frame semantics and transforms.
\item Evaluation planning and dependency closure.
\item Deterministic semantic/evaluation/result identity.
\item Cache and invalidation semantics.
\item Authoritative results, provenance, topology evolution, and diagnostics.
\item Drawing and PMI meaning.
\item Product Structure and BOM semantics.
\item Integration contracts consumed by Sheet Metal, CAM, Simulation, and PLM.
\end{itemize}

The mathematical kernel supplies computations, not these meanings.

\section{Science}
Science owns scientific facts and services that can be reused by multiple engineering domains. Material and physical properties belong here. The Phenomena Simulation Service is an abstract, provider-neutral service boundary.

\section{Phenomena Simulation Service}

The stable boundary is:

\begin{lstlisting}
Engineering Consumer
        -> IPhenomenaSimulationService
        -> IPhenomenaSimulationProvider
        -> Simulation Implementation
\end{lstlisting}

The service does not encode whether the provider is internal, external, CPU-based, GPU-based, specialized, or remote. Provider identity, execution detail, and transport belong behind the contract unless the service explicitly makes them semantic inputs.

A simulation result must carry enough identity, inputs, assumptions, and provenance for the consumer to decide whether the result is applicable. A visually plausible scalar without provenance is not an authoritative engineering result.

\section{Engineering Resources}

Engineering Resources own reusable manufacturing/engineering facts and capability declarations:

\begin{itemize}
\item Machine.
\item Tool.
\item Fixture.
\item Process.
\item Capabilities.
\end{itemize}

CAM and Sheet Metal consume these resources; the resource model must not become hidden CAM state.

\section{Sheet Metal}

Sheet Metal owns sheet-metal design semantics. It consumes engineering resources and applicable science/simulation contracts. Material/machine/process feasibility validation is a cross-domain responsibility implemented through explicit contracts, not by allowing Sheet Metal or CAM to become a second CAD kernel.

\section{CAM}

CAM consumes authoritative CAD semantics, product structure/BOM, engineering resources, material/process information, applicable Sheet Metal outputs, and the Phenomena Simulation Service where needed.

The manufacturing chain is:

\begin{lstlisting}
Manufacturing Definition
        -> Toolpath
        -> Postprocessor
        -> Deterministic G-code / NC
\end{lstlisting}

The postprocessor is a semantic boundary. Machine configuration, tool, fixture, process, coordinate system, operation order, postprocessor version/configuration, and other declared deterministic inputs must participate in the relevant identity. A renderable toolpath is not itself machine-ready NC.

\section{CAD Product Structure and BOM}

Product Structure owns product composition. BOM is a derived semantic view:

\begin{lstlisting}
CAD Product Structure
        -> BOM
        -> Drawing / CAM / PLM
\end{lstlisting}

BOM must not be a competing source of truth. Quantities, variants, configuration, occurrence identity, and product references remain traceable to the authoritative product state.

\section{Drawing and PMI}

Drawing consumes authoritative CAD and product semantics. It may derive geometry, sections, dimensions, annotations, and BOM views for documentation, but it must not reconstruct engineering truth from presentation meshes. Drawing details are mapped against the declared external capability set; the viewer remains downstream.

\section{PLM}
PLM consumes authoritative product, revision, lifecycle, configuration, and related engineering metadata. It may own lifecycle/workflow records but does not become geometric authority.

\section{Specification}
Specification stores intent: definitions, parameters, constraints, references, configuration, declared relationships, and source identity. It should not store hidden mutable evaluation state.

\section{Evaluation}
Evaluation resolves dependencies, constructs deterministic requests, calls the canonical evaluator/adapter, integrates authoritative results, and computes derived assets when required.

\section{Authoritative Result}
An authoritative result is trusted semantic evidence. It must identify what was evaluated, under which inputs and configuration, with which authority, status, and provenance. Topology and reference correspondence are evidence, not guesses.

\section{Representation}
Representation is disposable consumer data. It may be regenerated without changing semantic truth. Rendering may use approximations that are unacceptable as authoritative geometry.

\chapter{References, Topology, Frames, and Identity}

\section{Reference semantics}
A reference is semantic. It is not an accidental array index. The system must be able to state the producer, expected result identity, semantic target, frame requirements, and selector restrictions.

Required resolution states are:
\begin{lstlisting}
Resolved
Missing
Ambiguous
Indeterminate
Unsupported
\end{lstlisting}
Arbitrary fallback is forbidden.

\section{Topology provenance}
When topology changes, a downstream consumer must have explicit correspondence/evolution evidence. Topology array order is never semantic identity.

The mathematical layer contains explicit topology support for vertices, edges, coedges, wires, faces, shells, incidence, orientation, closure, shell connectivity, and certified planar/solid domains. Broader curved-face sewing and unrestricted topology construction remain separate contracts.

\section{Coordinate-frame semantics}
Where applicable, distinguish World, Document, Part, Body, Sketch, Face, Occurrence, Drawing View, and Simulation frames. Feature direction is an oriented semantic value, not an interpretation of viewer camera state.

\section{Deterministic identities}
The current .NET Framework canonicalization is explicit:
\begin{enumerate}
\item validate required IDs and definitions;
\item sort configuration and semantic collections by ordinal identity;
\item serialize canonical semantic content using camel-case JSON without indentation;
\item compute SHA-256 over canonical bytes;
\item attach the resulting lowercase hexadecimal value as \texttt{BuildIdentity}.
\end{enumerate}
The canonical semantic schema is \texttt{uml-cad-semantic/1.2.0}; the current bridge package is \texttt{uml-cad-build-package/1.0.0}; the compiled model schema is \texttt{uml-cad-compiled-model/1.1.0}.

\section{Builder validation}
The current builder rejects empty/whitespace required values, duplicate definition IDs across parts and assemblies, duplicate occurrence IDs within an assembly, references to unknown definitions, and circular assembly references.

\section{Part semantics}
A part contains sorted parameters, geometry descriptors, constraints, references, components, part type, name, and structured metadata. Metadata supports part number, description, material, manufacturer, vendor, revision, lifecycle state, author, document code, and custom properties.

The current Framework geometry/constraint descriptors are semantic descriptions. They are not the Rust mathematical geometry types. This is the intended separation between system meaning and mathematical execution.

\section{Assembly semantics}
Assemblies contain occurrences. Each occurrence has definition identity/type, stable name/ID, transform, metadata, optional configuration, quantity, BOM structure, visibility/suppression, grounded state, and flexibility state. Nested assemblies are recursively represented.

\section{Drawing semantics}
A drawing contains stable sheets, part references, and settings. Sheets contain IDs, names, drawing references, and settings.

\section{Build history}
\pathref{dotnet/src/UMLCAD.Framework/Semantics/BuildHistory.cs} stores build snapshots in a synchronized in-memory history. Sequence numbers identify history entries and are deliberately not used as semantic build identity.

\chapter{Compiled Model Contract}

\pathref{dotnet/src/UMLCAD.Framework/Semantics/CompiledModel.cs} defines the current compiled-result graph.

\section{Package}
\texttt{CompiledModelPackage} contains schema, application identity, build identity, manifest, optional render artifact, and diagnostics.

\section{Manifest}
\texttt{CompiledModelManifest} contains root node IDs, nodes, relationships, representations, topology bindings, source bindings, diagnostics, and repeated application/build identity.

\section{Nodes and relationships}
\texttt{CompiledNode} carries ID, name, kind, parent/children, metadata, relationship IDs, representation IDs, capabilities, optional source, and state. \texttt{CompiledRelationship} carries a stable relationship ID, source ID, target IDs, kind, and metadata.

\section{Representations and provenance}
\texttt{CompiledRepresentation} identifies a consumer artifact, render node, bounds, capabilities, and selectable sub-targets. \texttt{CompiledTopologyBinding} bridges a semantic node to a render primitive and includes topology kind, artifact identity, naming/nomenclature, optional number, bounds, and metadata. This bridge never becomes geometry authority.

\section{Graph construction}
The compiler:
\begin{enumerate}
\item emits parts and assemblies in stable ordinal ID order;
\item creates URI-encoded definition IDs;
\item creates deterministic occurrence IDs;
\item recursively emits nested assembly and part children;
\item emits explicit constraint-reference relationships;
\item identifies root definitions not referenced by another assembly;
\item validates parent/child consistency and relationship resolution;
\item rejects duplicate node IDs.
\end{enumerate}
URI encoding prevents colons/slashes in user identifiers from causing structural collisions.

\section{Authority law}

\section{Solver authority}
\pathref{kernel/math/solver.rs} uses the analytic Jacobian for the supported production equation set. \texttt{SolveOptions} defaults to 100 iterations, residual tolerance \texttt{1e-8}, step tolerance \texttt{1e-10}, and initial damping \texttt{1e-3}. \texttt{finite\_difference\_step} is retained for API compatibility and independent verification; it is not the production Jacobian generator.

Production linearization applies a declared semantic row scale to both the Jacobian row and matching residual row before the existing \texttt{nalgebra}-backed damped SVD solve. Rank, nullity, conditioning, accepted-step history, terminal residual/step evidence, and contradictory-state rejection are explicit authority concepts.

\section{Tolerances and numerical state}

\chapter{Dependency and Authority Rules}

\begin{lstlisting}
Platform
    ->
Mathematics
    ->
Science
    ->
CAD semantics / Product Structure
    ->
Engineering Resources
    ->
Specialized Engineering Domains
    ->
Application / Workflow / Presentation
\end{lstlisting}

These arrows express authority/consumption direction, not necessarily project references.

Mandatory rules:
\begin{itemize}
\item .NET semantic domains consume stable contracts rather than concrete Rust/vendor implementations.
\item The viewer never becomes the source of geometry, topology, manufacturing, material, or physical truth.
\item No domain creates a hidden second solver or geometry kernel.
\item OCCT structures remain behind adapters/contracts.
\item Legacy TypeScript functionality does not become a competing canonical System-CAD engine.
\item Compatibility package formats do not automatically become the long-term semantic authority.
\end{itemize}

\chapter{Persistence, Identity, and Lifecycle}

Current Framework build history is in-memory. It stores sequence, timestamp, snapshot, and package/build identity.

The target lifecycle model must keep distinct:
\begin{itemize}
\item object/definition identity;
\item revision identity;
\item build/evaluation identity;
\item authoritative result identity;
\item representation identity;
\item provider/external identity;
\item lifecycle state.
\end{itemize}

A database surrogate key or timestamp must not become a substitute for deterministic semantic identity.

\chapter{Coordinate, Transform, and Occurrence Semantics}

Current assembly occurrences store a 4-by-4 transform and reject non-finite matrices and an invalid homogeneous component.

The target system must preserve explicit frame semantics across World, Document, Part, Body, Sketch, Face, Occurrence, Drawing View, Manufacturing Setup, and Simulation contexts.

An occurrence transform places an instance; it does not mutate the source part definition.

A drawing view is not a new solid. A manufacturing coordinate system is not the source CAD frame. A simulation frame is not a viewer camera.

\chapter{Source Provenance and Auditability}

Compiled nodes can carry source binding information: file, symbol, source span, and revision.

The purpose is traceability:

\begin{lstlisting}
consumer result
    ->
semantic node
    ->
source binding
    ->
source revision
\end{lstlisting}

Source provenance explains origin but must not replace semantic identity.

\chapter{Representation and Viewer Boundary}

The current compiled model supports representation descriptors and an optional render artifact.

A render artifact can carry artifact identity, build identity, format/media type, asset identity, size/integrity metadata, URI or inline data, and additional properties.

Presentation consumers may select, focus, hide, and inspect derived assets. They must not decide topology correspondence, reference resolution, feature direction, manufacturing process, material truth, or whether a failed authoritative result should be displayed as success.

\chapter{Documentation and Agent Discipline}

The repository is the shared memory of independent engineering agents.

\section{Change law}

Every substantial change follows:

\begin{lstlisting}
Read governing docs
-> Inspect current code/tests
-> Define authoritative RED
-> Run RED
-> Implement smallest complete path
-> GREEN
-> Red-team
-> Complete E2E
-> Full applicable gates
-> Record exact evidence
\end{lstlisting}

\section{Branch and merge law}
Agents should work in isolated branches/worktrees where practical. A merge is an acceptance event. It must be based on exact validated commit state.

\section{No private dependency}
Agents communicate through repository artifacts: contracts, tests, fixtures, documentation, evidence, and exact commit SHAs. No implementation should depend on another agent's private reasoning or an undocumented assumption.

\chapter{Definition of Done}

A System-CAD capability is complete only when applicable gates are satisfied:

\begin{lstlisting}
Semantic contract
AND correct ownership/layer
AND implementation
AND required mathematical authority
AND reference behavior
AND frame/configuration behavior
AND deterministic identity
AND cache/invalidation
AND dependency/update behavior
AND authoritative result
AND provenance/topology evidence
AND derived representation where required
AND component tests
AND red-team tests
AND complete Python E2E
AND full applicable repository validation

\end{lstlisting}

Permitted status labels are:

\begin{lstlisting}

\end{lstlisting}

Never substitute a percentage for a gate.

\chapter{Known Limits and Explicit Non-Claims}

\begin{enumerate}
\item The repository is not yet a full CATIA-scale System-CAD application.
\item The current audited \texttt{main} tree does not contain every future specialized .NET domain project described by the target architecture.
\item Framework build/compiled-model functionality is not by itself a canonical feature-evaluation engine.
\item \texttt{uml-cad-build-package/1.0.0} is a current compatibility bridge, not a mandate for the long-term System-CAD semantic model.
\item General curved-face sewing, unrestricted B-Rep Boolean construction, arbitrary topology-aware fillet/chamfer, universal trimmed-surface filling, and universal closest-point/intersection solving are not silently certified by M0-M16.
\item Metal hardware validation does not make Metal an authoritative f64 geometry backend.
\item CUDA hardware validation remains unclaimed without an actual NVIDIA runner execution record.
\item Representation and tessellation are derived/approximate domains and never replace semantic truth.
\item This handbook does not define a competing feature sequence. \pathref{docs/SYSTEM_CAD_ARCHITECTURE.md} defines the intended architecture; the continuation/gap state at the exact \texttt{main} head determines the next implementation increment.
\end{enumerate}

\chapter{Final Architectural Invariants}

\begin{enumerate}
\item The Rust kernel is a thin mathematical authority; the .NET system owns CAD/engineering meaning and orchestration.
\item CPU f64 is normative for declared mathematical contracts.
\item GPU is acceleration only.
\item OCCT is backend/oracle infrastructure, never the system semantic authority.
\item Specification, Evaluation, Authoritative Result, and Representation remain distinct.
\item References are semantic and fail closed when missing, stale, ambiguous, unsupported, or indeterminate.
\item Topology array order is never semantic identity.
\item Frames and orientation are explicit semantic inputs.
\item Every authoritative semantic input participates in deterministic identity.
\item Full and incremental recomputation are two executions of one semantic function.
\item Cache hit and fresh evaluation are equivalent for the same identity.
\item Failure to prove correctness produces explicit non-success.
\item Science owns reusable material/physical facts and the provider-neutral Phenomena Simulation Service.
\item Simulation supports multiple interchangeable providers behind stable contracts.
\item Engineering Resources owns Machine, Tool, Fixture, Process, and Capability facts.
\item Sheet Metal consumes authoritative CAD, Science, and Engineering Resources through explicit contracts.
\item CAM consumes authoritative CAD/Product/BOM/resources/science and emits deterministic G-code/NC through the postprocessor boundary.
\item Product Structure is authoritative for composition.
\item BOM is derived from Product Structure and consumed by Drawing, CAM, PLM, and other downstream domains.
\item Drawing consumes authoritative CAD/product state and does not reconstruct semantic truth from presentation geometry.
\item PLM owns lifecycle/product integration without becoming geometry authority.
\item The viewer is presentation only.
\item The active System-CAD architecture document determines ownership and dependency direction; the exact \texttt{main} continuation/gap state determines what is implemented next.
\end{enumerate}

\section{.NET library invariants}

\begin{enumerate}
\item Framework owns semantic meaning; Kernel Client owns transport.
\item Builder-stage mutable definitions do not leak as public semantic state.
\item Semantic IDs use ordinal comparison and deterministic ordering.
\item BuildIdentity is SHA-256 of canonical semantic content.
\item History sequence is not semantic identity.
\item Assembly occurrence identity is contextual instance identity, not definition identity.
\item Transform structure is validated at the semantic boundary.
\item Compiled graph relationships are explicit and referentially validated.
\item Render artifacts are bound to BuildIdentity but remain derived data.
\item Kernel responses are rejected when valid JSON does not equal a valid result.
\item The .NET libraries must not implement a duplicate mathematical kernel.
\end{enumerate}
